# Seal Harness 独立应用接入规范

本规范定义 Seal Harness 中“应用”的产品和工程边界。它是后续应用接入的目标契约；当前 `@seal-harness/apps` 只实现了 DBX 的专用流程，不能据此宣称通用应用接入已经完成。DBX 的现状和回归要求另见 [本机应用管理](application-management.md)。

## 定义与插件边界

- **应用**是有独立产品身份、版本、发布物、主进程和界面的桌面程序。它可以由 Python、C++、Electron 等技术构成，也可以包含本地服务、模型和资源文件；“编译成二进制”不要求所有文件合为一个 exe，但交付物必须能在目标系统上安装和启动。
- **插件**运行在 Seal Harness 的扩展体系中，提供 Host 服务、工具、连接器或界面槽位。应用的 GIS、建模、数据库等业务代码及其主界面由应用自身拥有，不为了出现在 Seal 中而移植成 Seal 插件。
- 应用可以带一层很薄的 Seal 接入插件，负责目录呈现、安装与启动、状态查询及可选的智能体接口。这层插件不是应用本体。只有网页链接、源码目录、MCP 服务或嵌入的 React 页面，均不能单独算作已接入的桌面应用。
- “内置应用”表示 Seal Harness 认可并在应用目录中提供的应用入口；应用程序可以随产品交付，也可以按需安装。是否预装由发布方案决定，不改变上述定义。

## 应用交付契约

每个应用应有稳定且唯一的应用 ID，并声明名称、发布者、版本、来源与许可、支持的操作系统和架构、安装包或内置资源、校验摘要、可执行入口，以及运行所需的组件。可选能力（例如 MCP、深链接或本地 HTTP 服务）须单独声明，不得因应用已安装就默认为可用。

当前代码尚无多应用通用的 manifest 格式或生命周期 API；DBX 的固定字段和 `id: 'dbx'` RPC 不能直接当作公共协议。实现下一款应用前，应据本规范确定带版本的清单格式、应用状态和安装/启动接口，并同步更新实现与回归测试，不能仅在前端添加卡片。

发布物应带齐其运行时、动态库和必要资源，或由安装器明确安装所需组件；不能把开发机的源码 checkout、虚拟环境、系统 Python/Node、未声明的 PATH 项或另一个正在运行的开发服务当作交付条件。大体积应用可以独立下载和安装，不必塞入 Seal Harness 主安装包。平台支持以实际发布物和验证记录为准，不从 Seal Harness 自身支持的平台推断应用也支持该平台。

应用目录只接受产品维护的可信条目。客户端不能提供任意下载 URL、可执行文件路径或启动参数来绕过目录校验。没有在线下载地址时，可以让用户选择本地发布包作为**输入来源**，但应用 ID、版本和发布清单摘要必须由 Seal 固定；安装器逐文件校验后复制到受管理目录，不能直接执行来源目录中的程序。下载、解压、安装和更新应验证来源与摘要，拒绝越界路径、符号链接或联接、重复文件和不合理的文件数量与体积；替换失败应保留可用的旧版。保留第三方许可证和归属信息。

## 安装、运行与数据

- Seal Harness 负责显示可用平台、安装状态和进度，并管理安装、启动、重开、更新及卸载。启动前重新校验受管理的程序入口；只启动属于该应用和当前账号的已安装版本。程序启动、界面打开和服务就绪是不同状态，失败时分别报告，不以“已打开”代替可用性检查。
- 应用自己的进程与 Seal Harness Host 分离。应用退出、崩溃或升级不能拖垮 Seal 主进程；Seal 退出时对自己启动的后台服务做有界、可观测的收尾，不强杀用户另行启动的实例或正在运行的业务任务。单实例应用要核对运行中的可执行文件身份，避免打开其他安装或账号的实例。
- 程序文件、账号数据和可共享的已校验安装包缓存分开存放。程序和数据目录以实际 `DSH_HOME` 为根并按本机账号隔离；工作目录应落在该应用的数据目录。生成结果、数据库、用户配置和凭据不能写进安装目录。升级和普通卸载默认保留用户数据；删除数据必须是另行明确的操作。清理只限当前应用受管理的路径。
- 应用若启动本地 HTTP 服务，应使用回环地址、避免固定端口冲突，并提供就绪与退出机制；接口需要防止其他本机网页或进程越权调用。远程访问、文件系统访问和凭据传递必须有明确边界，不能因应用在 Seal 中出现就继承 Seal 的全部权限。

## 与 Seal Harness 会话的集成

应用界面可以完全独立于 Seal Harness 的主内容页。应用中心的“打开”应启动或聚焦应用自己的桌面窗口，让用户在 Seal Harness 中发现并进入它；把网页嵌入 Seal 主界面是另一项界面集成选择，不能代替可独立运行的桌面交付物。

应用可以选择提供 MCP 或其他受控接口供 Seal 原生会话使用。安装应用、启动应用、连接工具和允许某个会话调用工具是四个不同动作与状态：按现有连接器的账号、会话选择和工具权限规则处理，不自动把应用能力授予所有会话。应用自身的模型服务、API Key 与 Seal Harness 凭据也不自动互通；若要共享，须定义显式授权与密钥传递方式，并避免在日志、URL 和页面中暴露密钥。应用没有智能体接口时，其桌面功能仍应可用。

## 完成标准

一个应用只有同时满足以下条件，才能称为“可在 Seal Harness 中使用”：

1. 在目标操作系统上，用发布物而非开发目录独立安装并启动，主要功能和必要资源可用。
2. Seal 的应用目录能准确显示支持平台、安装状态和错误；安装后从“打开”进入该应用的真实界面，重启 Seal 后仍能恢复已安装状态。
3. 真实验证启动、就绪、关闭或退出、重开、升级与失败回滚、卸载与数据保留、账号隔离和路径安全；若提供 MCP，还要验证连接、权限、断连和恢复。
4. 构建、安装包和已安装实例分别验证。某台开发机上的源码运行、应用卡片展示或一次进程启动，都不能替代发布物验收；未验证的平台明确标注未支持或未验证。

BuildingBuilt 是此类应用：它需要独立桌面发布物及运行时、模型资源、切片程序、可配置的数据目录和受管理的服务生命周期。当前只有 Windows `Open*` 切片程序时，先按 Windows 发布物验收。其发布包独立分发，Seal 通过固定清单从本地发布目录安装，不增加 Seal 安装包体积；在线地址以后可独立配置。Seal 原生会话调用建模流程属于可选的进一步集成，不是应用成立的前提。
