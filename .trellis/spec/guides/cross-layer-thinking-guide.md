# 跨层检查

修改前沿实际数据流追踪生产者、消费者和边界；三层以上、多个客户端或打包/运行时交叉的功能尤其需要检查。

## 数据与行为

- 记录数据从配置、插件、Host 到 Client 的实际路径，核对类型、序列化和错误传播。
- 对事件、JSONL、RPC 和外部配置使用已有明确结构，在信任边界解析；内部不要重复校验或强制转换未知字段。
- descriptor 含有本地可执行文件时，除结构校验外，还要检查解包后的真实路径、工作区边界和最终执行参数；不能只验证 UI 表单。
- 含外部进程和持久状态的初始化流程，检查“外部操作已成功、内部提交失败”的断点，并为可恢复状态保留明确回滚路径。
- 菜单到确认弹窗跨组件卸载时，要模拟菜单先关闭、再确认的真实事件顺序；不能只在同一组件里直接调用按钮回调。
- 新状态或枚举值需搜索所有分支与默认行为。可推导状态只有一个来源。
- 复核错误是否可重试、是否会丢失数据，以及界面是否给出可执行的下一步。
- 远端探测区分不存在与暂时失败，交互和非交互入口保持同样的错误语义。读取完整元数据后解析，不用任意截断片段当作完整 JSON。

## 产品与打包

- 产品身份、默认数据目录、图标、安装器、bundle/profile 和更新渠道必须一致。
- Windows 桌面身份还涉及开始菜单 Shell Link、AppUserModelID 与目标可执行文件；不要只凭窗口图标判断品牌已完整替换。
- 公开插件接口先于上游修改；产品组合不能通过深度引用上游源码绕过边界。
- 编译、开发启动和最终安装包分别检查依赖可达性。原生模块、签名和平台行为需要对应系统验证。
- 共享 Stable/Beta 改动按根规则同步，Next 与Seal Harness专属行为不混入镜像。
- 上游升级同时检查公开接口、插件加载、启动、对话、退出和升级路径。

## 工作流与生成配置

- 修改运行时解析的模板时，检查所有消费者和实际输出，不只检查写入端。
- Trellis 的阶段标题、状态标签、技能路由和 hook 提示要一致；用 `get_context.py --mode phase --step <X.Y>` 验证解析。
- 升级工具时保留本地适配，检查模板哈希与不存在路径。不要把 Trellis 自身源码示例当作Seal Harness目录。
- 需要版本化文档时，路由、版本标签和真实内容必须对应同一版本。

审查发现必须回到代码验证。先查数据来源和设计约束，再判断校验是否缺失；不要把内部已约束数据误当成外部输入。
