# 代码复用检查

先理解调用链，再决定是否抽取。复用的前提是业务含义和变化规则相同，少量重复优于错误抽象。

## 修改前

- 用 `rg` 搜索相关常量、配置、函数和所有调用方，核对已有依赖与公开扩展点。
- 先复用标准库、平台能力和已安装依赖。只有真实需求不能满足时才新增实现。
- Seal Harness产品行为先在 `seal-harness-desktop/` 实现。插件独立、可复用且有明确边界后再提取到根 `packages/`。
- 不深度导入上游源码，不为单一实现增加工厂、接口或配置开关。
- 同一概念保留一个可信来源；可推导数据不要另存一份同步。

## 修改后

- 改动枚举、事件、配置或公共类型时，搜索所有分支、消费者和默认行为。未知外部值应在边界明确处理，不依赖意外的 `else`。
- 多条路径生成相同产物时，优先复用同一数据源或生成入口；否则验证产物一致，特别是首次初始化与后续升级。
- 修复应落在所有调用方共用的根因处，避免只修复报告中的一个入口。
- 检查新导入的方向、循环依赖和打包可达性。构建时存在的包必须在最终产物中也可加载。
- 测试应能在行为破坏时失败，不用字符串匹配代替编译或运行时检查。

本仓库部署 Trellis 工具，不维护 Trellis CLI 模板源码。修改本地工作流后验证脚本、hooks 和技能的一致性，不创建或同步不存在的 `packages/cli` 模板目录。
